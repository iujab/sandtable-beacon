# Puck hardware, hosts and geometry (Sandtable Beacon)

Research date: 2026-11-14. Scope: DWM3001CDK pucks, puck hosts (Arduino UNO Q, Android phone, battery bank), and geometry numbers for the simulator. The iOS / Nearby Interaction side is covered in `ios_ni.md` and is not repeated here.

Status: complete for tonight (2026-11-14). qorvo.com returned HTTP 429 to automated fetches, so Qorvo facts come from the Qorvo forum, a Qorvo product brief hosted by FiRa, a distributor copy of the DW3000 datasheet and Zephyr docs. Lines marked "derived" are calculations, not sourced claims.

## 1. DWM3001CDK board facts

Plain answer: the board has two micro-USB ports. J9 (bottom, labelled "J-Link") goes to the on-board SEGGER J-Link OB, which gives flashing, debugging, RTT and a virtual COM port wired to the module's UART. J20 (upper, nearer the module) goes to the nRF52833's own USB, which only enumerates if the firmware implements USB CDC (the CLI firmware does; QANI does not). Either USB port powers the board; a battery connector and the Raspberry Pi header are alternatives. The UWB chip is a single-antenna DW3110 (no PDoA), channels 5 and 9. Drag-and-drop flashing is not reliable on this board; plan on SEGGER J-Flash Lite or JLinkExe, which are free and run on macOS (Apple Silicon native), Windows and Linux arm64.

- "Two micro-USB ports connect to the J-Link and DWM3001C USB interface. An on-board J-Link debugger provides SWD and UART interfaces to the DWM3001C ... The board can be powered from either of these USB ports, a Raspberry Pi interface, a battery or an external power supply." Product brief Rev. B, May 2022. https://www.firaconsortium.org/sites/default/files/2024-08/DWM3001CDK%20Product%20Brief.pdf
- Same brief: "26 pin Raspberry Pi compatible header", "Reset and user-defined buttons and LEDs", "Measure module current via header on VCC trace", "Supports UWB RF bands 5 (6.5 GHz) and 9 (8 GHz)", "nRF52833 Soc with Bluetooth 5.2", "Two integrated antennas for BLE and UWB" (that is, one UWB antenna and one BLE antenna, both on the module). Same URL.
- J-Link port: "Connect to the bottom micro-USB port labeled as J-Link"; "the board comes with J-Link OB adding debugging and Virtual COM Port capabilities"; console at 115200 baud, `/dev/ttyACM0` on Linux. Supported runners: J-Link (flash, debug, RTT), nrfjprog, nrfutil, OpenOCD, pyOCD. Zephyr board page, which also says the board has a "battery connector and charging circuit". https://docs.zephyrproject.org/latest/boards/qorvo/decawave_dwm3001cdk/doc/index.html
- J20 is the nRF52833 native USB: "J20 is the User USB, where the CLI application implements the Virtual COM Port" (Qorvo forum); a demo repo says the upper port "(labelled J20) (this is the nRF52833's USB port)". https://forum.qorvo.com/t/getting-started-with-the-dwm3001c/13430 and https://www.github.com/Uberi/DWM3001CDK-demo-firmware
- Battery: the Quick Start Guide (search snippet; PDF timed out) lists a battery connector and says the board has no battery charger, which conflicts with the Zephyr page. https://www.mouser.com/datasheet/2/412/Qovro_7_7_2022_DWM3001CDK_Quick_Start_Guide-2998998.pdf . The module takes 2.5 to 3.6 V (forum paraphrase of the datasheet). https://forum.qorvo.com/t/does-any-one-know-where-to-find-the-offical-power-requirement-of-the-dwm3001cdk/13973
- Current draw, UWB chip only (DW3000 datasheet v1.1, Decawave/Qorvo, read from a distributor mirror because qorvo.com returned HTTP 429): receive peaks about 70 to 78 mA, TX tens of mA, the typical DS-TWR initiator profile shows 48 mA and 78 mA peaks with 18 mA IDLE PLL between frames and 260 nA sleep, all at 3.0 V. https://atta.szlcsc.com/upload/public/pdf/source/20220621/2EAA42E8F3E2D83DDB8686FF8DCFAD44.pdf (original: https://www.qorvo.com/products/p/DW3000)
- Current draw, rest of the board: the J-Link OB chip draws "something around 10-15mA (if recall it correctly)" (forum, 2023, from memory). No official whole-board figure for idle, BLE advertising or ranging was found. https://forum.qorvo.com/t/does-any-one-know-where-to-find-the-offical-power-requirement-of-the-dwm3001cdk/13973
- Single antenna, no PDoA: DW3000 datasheet Table 1 lists "DW3110 ... PDoA support: No" and "DW3120 ... Yes"; "A variant of the IC is available which has two RF antenna ports and is used for Phase Difference of Arrival". Same mirror URL as above. The product brief says the module is "based on the Qorvo DW3110 IC".
- Flashing: one forum user reports "J-Link OB drag and drop doesn't work" on this board because it does not show up as a flash drive; forum posts recommend J-Flash Lite. https://forum.qorvo.com/t/getting-started-with-dwm3001cdke/11801 . ## 2. Qorvo firmware images and what they print

Plain answer: there are two families. (a) The Nearby Interaction firmware (QANI / QNI, for example `DWM3001CDK-QANI-FreeRTOS_full_QNI_3_0_0.hex`) logs over SEGGER RTT on the J-Link port J9, not over a serial port; reading it needs J-Link software (JLinkRTTLogger / JLinkRTTViewer, also available for Linux arm64, so the UNO Q can read it). An early NI release printed a JSON line per ranging round with a distance field, but no line from QNI 3.0 with a distance was found. (b) The DW3_QM33 SDK "CLI" firmware speaks a text CLI (INITF, RESPF, LISTENER, SAVE, UART ...) on USB CDC on J20 and prints JSON lines with `D_cm`; two boards can range each other with it (one INITF, one RESPF) with no code change. The SDK is a gated download (request form, one-time link, non-Gmail address preferred), so it may not be obtainable tonight.

- QANI logs over RTT: "by default, ranging information from the Qorvo module is available via the JLink connector" (user, viewed with JLinkRTTViewer); reply: "QNI uses a rtt_reporter task to print all the info", whereas the CLI preview uses a usb_reporter. https://forum.qorvo.com/t/dwm3001cdk-nearby-interaction-trying-to-get-ranging-via-usb-uart/13613
- "QANI doesn't have usb uart support DW3 does" (forum, search snippet). https://forum.qorvo.com/t/dwm3001cdk-nearby-interaction-trying-to-get-ranging-via-usb-uart/13613
- Example RTT lines from the 2022 "Qorvo_Apple_Nearby_Interaction_1.0.0" firmware: `{"TWR": {"R":6613,"a16":"0x0001","S":"ERR","D cm":0}}` and `ACCESSORY_RANGING_ROLE: Initiator`. Qorvo reply: the preloaded sample "is to be used with an iPhone equipped with a U1 UWB chip"; two boards do not range each other on it without code changes. https://forum.qorvo.com/t/dwm3001cdk-what-should-i-do-to-start-ranging-between-the-two-boards/12439
- CLI firmware port: "User USB (J20)", the PC sees a new COM port; a CLI hex cited by users: `DWM3001CDK-DW3_QM33_SDK_CLI-FreeRTOS_0_1_1.hex`. Example JSON result: `"Addr":"0x0000","Status":"Ok","D_cm":61` with `LPDoA_deg`, `LAoA_deg`, `LFoM`, `RAoA_deg`, `CFO_100ppm` (AoA fields are meaningless on the single-antenna DW3110). SDK guide quoted for UCI over UART: "115200,8N1, no flow control". https://forum.qorvo.com/t/getting-started-with-the-dwm3001c/13430
- On failure, the status is e.g. "RX_TIMEOUT" and the distance field is absent. Qorvo staff (2025-07-22): INITF/RESPF are "CLI command and meant for being human readable"; use the UCI build for programs ("way easier to handle for a program", with Python scripts). https://forum.qorvo.com/t/is-there-any-documentation-for-the-format-of-the-initf-respf-log-message/22984
- Multi-board: INITF/RESPF take `-ADDR=` style arguments (`-ADDR=1` on the first anchor, 2 on the second ...); typing `save` while a session runs stores it for boot-up autostart. https://forum.qorvo.com/t/dwm3001cdk-cli-command-that-starts-automatically-on-boot-up/23591 and https://forum.qorvo.com/t/remember-previous-settings-after-power-cycle/17894
- Version caveat: a user reports INITF fails with SDK 1.1.0 and 1.1.1 CLI binaries but works with SDK 1.0.2. https://forum.qorvo.com/t/fira-applications-initf-in-dw3-qm33-sdk-1-1-0-and-1-1-1/24933
- UART on the header pins is disabled by default ("configured by default to use USB CDC"). https://forum.qorvo.com/t/dwm3001cdk-uci-enable-gpio-uart-serial-communication-via-raspberry-header/22871
- Accuracy note from Qorvo: modules are factory calibrated with values in OTP (read with `GETOTP`); users still report 40 to 50 cm errors in some setups. https://forum.qorvo.com/t/how-to-reduce-distance-d-cm-error/20404
- Download gating: users must request the SDK; a one-time emailed link; non-Gmail address preferred; the checkpoint page sometimes blocks the download. https://forum.qorvo.com/t/unable-to-download-dw3-qm33-sdk-1-1-1-ra007127/26201 and https://forum.qorvo.com/t/qm33-dk-software-sources-tools-and-developer-guide-update-download-problem/19145 . The QNI package has the same problem for personal email addresses (see `ios_ni.md`, forum topic 25771).

Not confirmed: the exact RTT line format and RTT channel of QNI 3.0.0 (whether it prints `D cm` per round when an iPhone is ranging); whether the CLI can be moved to the J-Link VCOM on J9 with the `UART` command (the brief says the J-Link OB has a UART link to the module, so it is plausible); the full INITF/RESPF argument list (it is in the gated Developer Manual).

## 3. Arduino UNO Q as a puck host

Plain answer: the UNO Q has one USB-C port that can role-switch to host, and its Debian side does see USB CDC devices as `/dev/ttyACM*` through a hub (community reports), so `pyserial` works when run over SSH, not inside the App Lab Python container. In host mode the board can source VBUS from its own 5 V rail, but the supported and reported-working setup is a USB-C hub/dongle with PD input (power in, pass-through), and host mode does not come up when the board is powered from VIN or the 5 V pin without a third-party fix. The radio is a Qualcomm WCN3980 (Wi-Fi 5, Bluetooth 5.1); one Qualcomm project runs a `bleak` BLE scanner on the Debian side over SSH. No figure for host-port current was found; one micro-USB DWM3001CDK (well under 200 mA) is a small load on a 5 V / 3 A PD supply.

- One USB-C port: "USB 3.1 with Role-Switching Capabilities"; USB PD "requests a 5 V / 3 A contract only"; inputs are USB-C VBUS (up to 3 A), VIN 7 to 24 V, or 5V_SYS pin; "A protected P-channel MOSFET (Q2801) can source USB VBUS from 5V_SYS when the board operates as a USB host/OTG"; for peripherals in SBC mode "use a USB-C dongle with external power delivery capabilities". Datasheet ABX00162/ABX00173, modified 13/11/2026. https://docs.arduino.cc/resources/datasheets/ABX00162-ABX00173-datasheet.pdf
- Radio: "WCBN3536A (Qualcomm WCN3980)", "Wi-Fi 5 802.11a/b/g/n/ac (dual-band) + Bluetooth 5.1"; "The wireless module uses SDIO for Wi-Fi data and a UART for Bluetooth control, with a shared PCB antenna". BLE TX 9.5 dBm. Same datasheet.
- OS: "QRB2210 ... quad-core Arm Cortex-A53 running Debian Linux OS"; RAM 2 or 4 GB. Same datasheet.
- User manual: any USB-C dongle with external power delivery can be used, "except Apple ones" (search snippet of a mirrored copy). https://ja-bots.com/wp-content/uploads/2026/03/UNO-Q-User-Manual-_-Arduino-Documentation.pdf
- `/dev/ttyACM*` seen: "Uno Q can see dev/ttyACM* but python scripts in App Lab are containerized" and the container "can't reliably see USB CDC" (community, 2026-03-13); others confirm Python sees the tty devices and recommend running a plain Linux script over SSH, or a socat serial-to-TCP bridge. `pyserial` (`serial.tools.list_ports`) was used. No Arduino staff reply. https://forum.arduino.cc/t/arduino-uno-q-app-lab-as-a-usb-host-to-an-uno-r3-python-environment-sees-0-devices/1433482
- Host mode and power source: when powered from VIN "the USB-C port does not function in host mode"; from the 5 V header the jack supplied no VBUS (one user); a USB 3.0 hub with PD input works; a third-party systemd fix writes `host` to `/sys/kernel/debug/usb/4e00000.usb/mode`; Arduino staff reportedly called VIN-powered host use "not a supported scenario"; quoted Arduino SBC page: "The UNO Q does not supply power to the USB-C dongle." https://forum.arduino.cc/t/uno-q-usb-port-not-working-if-board-powered-from-5v/1442207
- Dongle issues exist in the forum (some hubs do not work). https://forum.arduino.cc/t/uno-q-usbc-dongle-issue/1410296
- BLE scanning: a Qualcomm developer project runs a Bleak-based BLE scanner on the UNO Q Debian shell over SSH because it "needs direct BLE and D-Bus access" (search summary). https://www.qualcomm.com/developer/project/building-a-practical-asset-tracking-system-with-arduino-uno-q . Bleak's Linux backend uses BlueZ over D-Bus. https://bleak.readthedocs.io/en/latest/backends/linux.html
- SEGGER J-Link software exists for Linux arm64 (DEB and TGZ), so the UNO Q can in principle run `JLinkRTTLogger` against a board on J9 to read QANI's RTT log. https://www.segger.com/news/seggers-complete-j-link-software-now-available-for-linux-on-arm/
- Battery banks: "Some large capacity power banks turn off their supply after a short period of time when detecting low current draw" (community, about a DWM3001CDK on battery). https://forum.qorvo.com/t/dwm3001cdk-board-transmits-slower-on-battery-power/22115 . The UNO Q wants 5 V / 3 A; "brief dips can cause resets or link drops" (datasheet).

Not confirmed: that the stock UNO Q kernel has `cdc_acm` built in (inferred from users seeing `/dev/ttyACM*`, which is the cdc_acm driver's device name, but no `lsmod` output was found); the current limit of the host-mode VBUS switch Q2801; that a bare USB-C-to-micro-B cable (no hub) puts the UNO Q into host mode while it is powered some other way; that BlueZ passive scanning (as opposed to active) works on the WCN3980 firmware; that SEGGER's J-Link OB is supported by the arm64 build on this kernel (likely, SEGGER says feature parity).

## 4. Android phone as a second puck host

Plain answer: as a power source, an Android phone with USB host (OTG) support will put 5 V on VBUS for a USB device, usually budgeted around 500 mA, which is plenty for one DWM3001CDK; you need a USB-C (plug, phone end) to micro-B cable or an OTG adapter. As a reader, Chrome for Android gained the Web Serial API in Chrome 148 (stable 5 May 2026), and WebUSB plus Google's `web-serial-polyfill` already worked for CDC-ACM devices. But the stock QANI firmware prints nothing on any serial port (it uses RTT, which needs the J-Link protocol), so an Android reader is only useful with the CLI firmware on J20. Verdict: not worth it tonight; use one plain USB battery bank per puck, and keep the Android phone as a spare power source or as the ranging peer for a FiRa demo later.

- Chrome 148 release notes: Web Serial "Now it is supported on Android"; covers ports on the system and "removable USB and Bluetooth devices that emulate a serial port"; Chrome 148 stable date "May 5th, 2026". https://developer.chrome.com/release-notes/148
- Intent to Ship (2026-03-24): milestone Chrome 148, Finch feature `WebSerialWiredDevicesAndroid`; a Chromium engineer: "The API will be available on Android 17 this year" and "only devices configured to expose wired serial ports will return non-empty lists of serial ports". That last sentence suggests that wired USB serial may depend on the Android version or device configuration. https://groups.google.com/a/chromium.org/g/blink-dev/c/HBJ-uYFvkpM
- Separate intent: Web Serial over Bluetooth RFCOMM on Android. https://groups.google.com/a/chromium.org/g/blink-dev/c/BqUGCcurReE
- Before 148: "Android itself doesn't provide applications with a serial API"; the polyfill runs over WebUSB, which Chromium on Android supports. https://groups.google.com/a/chromium.org/g/chromium-dev/c/iS3HhY_Tm6E . The polyfill "only currently supports USB CDC-ACM devices" (interface class 2). https://github.com/google/web-serial-polyfill/issues/29 and https://www.npmjs.com/package/web-serial-polyfill
- SEGGER offers J-Link WebUSB, but only for flashing ("an easy cross-platform alternative to MSD drag & drop programming"); it does not mention RTT, VCOM or Android. https://kb.segger.com/J-Link_WebUSB
- No evidence was found of anyone opening a J-Link OB virtual COM port, or reading RTT, from Chrome on Android.
- OTG power: USB 2.0 ports budget 500 mA; phone OTG limits vary, and some phones cut VBUS in software above about 500 mA (community). https://arachnoid.com/usb_power/index.html
- Secure context: Web Serial and WebUSB need https or `localhost`; `adb reverse tcp:PORT tcp:PORT` lets the phone open `http://localhost:PORT` served from a laptop. (Standard Chrome behaviour, not re-read tonight: https://developer.chrome.com/docs/capabilities/serial and https://developer.android.com/tools/adb .)

Not confirmed: whether wired Web Serial works on the owner's unknown Android model and version (the Intent to Ship ties it to Android 17 and device configuration); OTG current limit of that phone; whether the J-Link OB's VCOM interface is claimable via WebUSB on Android.

## 5. Geometry numbers

Plain answer: for the simulator, use a random range error of about 2 to 5 cm (1 sigma) for a calibrated DW3000 link in clean line of sight, and 13 to 15 cm for phone-to-accessory links in ordinary rooms, plus a static per-link bias of about plus or minus 6 cm after calibration (plus or minus 15 cm uncalibrated), an orientation-dependent bias of 5 to 25 cm, a non-line-of-sight bias of about +35 to +50 cm (sigma 35 to 60 cm) through obstacles, and rare outliers of metres. Bearing from two single-antenna boards on one rigid puck follows sigma_theta = sqrt(2) * sigma_r / (b * |sin theta|); with a 30 cm baseline that is about 4 degrees at best (datasheet sigma) and 14 degrees with realistic 5 cm sigma, and an uncalibrated 10 cm differential bias alone tilts the bearing by about 19 degrees. The DWM3001C's DW3110 has one antenna and no PDoA. Two anchors a few metres apart give a mirror ambiguity and an error that grows fast along the baseline direction for distant targets and across it near the baseline line.

### 5a. Ranging error

- DW3000 datasheet v1.1, Table 14: ranging accuracy "+/- 6 cm" "After calibration is applied. Approximately +/-15cm without calibration"; ranging standard deviation 1.5 cm "measured at -85 dBm power level", "In line of sight conditions". https://atta.szlcsc.com/upload/public/pdf/source/20220621/2EAA42E8F3E2D83DDB8686FF8DCFAD44.pdf
- Smartphone vs DW3000 study (arXiv 2303.11220, uncalibrated, mixed environments): mean SD DW3000 14.03 cm, Pixel 6 Pro 13.04 cm, Galaxy S21 Ultra 13.63 cm, iPhone 12 Pro 15.02 cm; RMSE 16.03 / 14.98 / 15.65 / 17.68 cm; iPhone SD "23 cm at the 5 m distance" outdoors; outliers up to -3 m (iPhone, Pixel) and up to 5 m short (Samsung); failures concentrated when the phone is rotated 90 to 270 degrees (its back or edge away). https://arxiv.org/html/2303.11220v1
- Same paper, related work: DW3000 in LOS mean error 4.1 cm, SD 4.1 cm; in NLOS mean error 34 cm, SD 35 cm. DW1000-era phone (BeSpoon): LOS mean 2.6 cm, SD 11 cm; NLOS mean 50 cm, SD 61 cm. DW1000 uncalibrated RMSE 28 to 54 cm, calibrated 4.3 to 14 cm. https://arxiv.org/html/2303.11220v1
- Orientation: "an error of up to 25 cm in distance can be attributed to the antenna orientation" (prior work cited in an EWSN 2020 paper). https://www.ewsn.org/file-repository/ewsn2020/156_161_schroder.pdf . A UWB vendor on the Qorvo forum: range "can shift by 5 to 10 cm with rotation" about the antenna axis. https://forum.qorvo.com/t/position-of-the-tag-keeps-changing/8712
- Antenna delay: "a one-nanosecond timestamping error corresponds to 30 cm in ranging error"; relative-pose-dependent bias can be mis-learned as antenna delay. https://arxiv.org/pdf/2210.05888
- iPhone U1/U2 to DWM3001CDK specifically: no controlled measurement of bias and sigma was found. Forum users report 40 to 50 cm errors on CLI ranging between boards in some setups. https://forum.qorvo.com/t/how-to-reduce-distance-d-cm-error/20404

Not confirmed: NLOS bias through a human body for DW3000 or iPhone (no primary number found; treat as similar to or larger than the 34 to 50 cm wall figures, with frequent dropouts); per-unit bias of iPhone 14 vs iPhone 15 to a DWM3001CDK.

### 5b. Bearing from two single-antenna nodes on one rigid puck (range difference)

- Model: nodes A and B at baseline b, target far away at angle theta from the baseline axis. Range difference delta_d = d_A - d_B ~ b cos(theta), so theta = arccos(delta_d / b), and sigma_theta ~ sigma_delta_d / (b |sin theta|), with sigma_delta_d = sqrt(2) sigma_r for independent links. Bias in delta_d (difference of the two per-link biases) is not reduced by averaging: angle bias ~ delta_bias / (b |sin theta|). Near-field (target within a few b) needs the exact hyperbola, not the arccos form. (Standard geometry; derived here.)
- Worked numbers, broadside (theta = 90 degrees); double them at theta = 30 or 150 degrees:

| sigma_r per link | b = 10 cm | b = 30 cm | b = 50 cm |
|---|---|---|---|
| 1.5 cm (datasheet LOS) | 12 deg | 4.1 deg | 2.4 deg |
| 5 cm (realistic LOS) | about 40 deg (useless) | 13.5 deg | 8.1 deg |
| 14 cm (phone, rooms) | useless | 38 deg | 23 deg |
| 10 cm uncorrected differential bias | 90 deg range, useless | 19 deg bias | 11.5 deg bias |

- Averaging N rounds cuts the random term by sqrt(N) only if the phone and multipath are static. With QANI each board runs its own session with the phone, so the two ranges are not simultaneous; a moving phone adds error.
- Closest measured example found: Microchip ATA8352 demo computes angle from the timestamp difference at two anchors 55 cm apart; "the angle resolution depends on the measured angle and is between 5.2 and 17.7 degrees" (165 ps timestamp step, about 4.95 cm per step). https://onlinedocs.microchip.com/oxy/GUID-3DEE8FD6-3D1E-4178-A506-A130BBE38229-en-US-2/GUID-16273F75-AD4C-412A-B8B6-5606E1EC8315.html
- A single-anchor study with two UWB modules in orthogonal directions reports distance accuracy under 1 m and angle errors below 10 degrees (search summary). https://www.cse.iitk.ac.in/users/amitangshu/Single_Anchor-Based_Infrastructure-less_Localization_Performance_using_UWB_Radios.pdf
- PDoA comparison: DW3000 datasheet gives PDoA accuracy +/- 10 degrees, SD 5 degrees, with AoA "better than the PDoA accuracy by a factor of approximately two"; PDoA needs the two-port DW3120 (or DW3220); DW3110 "PDoA support: No". https://atta.szlcsc.com/upload/public/pdf/source/20220621/2EAA42E8F3E2D83DDB8686FF8DCFAD44.pdf . A DW3220-based node reports 2.4 degrees average angular accuracy over a 90 degree sector. https://arxiv.org/pdf/2312.13672 . Qorvo suggests about 0.45 lambda antenna spacing for AoA (secondary summary of APH511). https://www.allaboutcircuits.com/industry-articles/designing-uwb-antennas-for-angle-of-arrival-applications/

Not confirmed: any paper that measured range-difference bearing from two independent DW3000 nodes 10 to 50 cm apart; none was found.

### 5c. Two anchors a few metres apart

- With anchor unit vectors at plus and minus beta from the perpendicular (beta = half the angle the baseline subtends at the target), the 2-D error is sigma_along = sigma_r / (sqrt(2) sin beta) and sigma_across = sigma_r / (sqrt(2) cos beta) (least-squares covariance sigma_r^2 (H^T H)^-1; derived here).
- Example: baseline 3 m, target 5 m out on the bisector: beta = 16.7 deg, sigma_along = 2.5 sigma_r, sigma_across = 0.74 sigma_r. At 10 m: sigma_along = 4.8 sigma_r. With sigma_r = 15 cm, about 0.7 m along-baseline error at 10 m.
- Near the line through both anchors, beta goes to 90 degrees and the across-baseline error goes to infinity; on the line itself the target is unobservable across it.
- Mirror ambiguity: two circle intersections, reflected across the anchor line. Resolve with floor-plan knowledge (one solution outside the building), a third puck, or the phone's own NI direction. Anchor positions are not known after a throw; QANI cannot range board to board, so self-survey needs the CLI/UCI firmware (gated download, section 2).

### 5d. iPhone direction (details in `ios_ni.md`)

- Apple publishes no degree accuracy for `direction`. WWDC20: the U1 field of view is "approximately the same as the Ultra Wide camera's field of view on the iPhone 11"; distance and direction are nil when confidence is very low or the peer is out of the field of view (session notes, search summary). https://developer.apple.com/videos/play/wwdc2020/10668/
- Camera assistance (`isCameraAssistanceEnabled`) uses ARKit "to provide a nearby object's distance and direction in a wider range of environmental conditions"; `horizontalAngle` is the azimuth in radians. https://developer.apple.com/documentation/nearbyinteraction/ninearbyaccessoryconfiguration/iscameraassistanceenabled and https://developer.apple.com/documentation/nearbyinteraction/ninearbyobject
- For a victim's phone in a pocket or in smoke, direction from the phone side is not available in practice (camera, light and motion needed; see `ios_ni.md`).

## 6. Throwing a board

Plain answer: no Qorvo guidance on ruggedising or throwing a DWM3001CDK was found. General UWB guidance is to keep metal (and batteries) a few millimetres to centimetres away from the antenna, never enclose it in metal, and keep the antenna at least about 15 cm above a ground plane such as a floor. A board lying flat on the floor is the worst case: the floor reflection arrives within millimetres of the direct path and partly cancels it, which weakens the first path and pushes the detector to a later path (long bias) or to dropouts. For tonight, stand each board upright on something 15 cm or more tall.

- "UWB signals don't do well when traveling right over a ground plane, it affects the speed of propagation"; "15 cm separation from the ground plane (be it actual ground or metal lath such as suspended ceiling grids) is required to mostly negate this behavior"; suggested test at 2+ m height; the useful path is a "rugby-ball" volume about 30 cm wide, with obstructions near the antennas mattering most. (UWB vendor, Qorvo forum, 2020-08-29.) https://forum.qorvo.com/t/position-of-the-tag-keeps-changing/8712
- Metal clearance: "at least 3mm from metal components or surfaces, and ideally 5mm"; antennas "will not work within fully enclosed metal enclosures" (Taoglas UWB antenna datasheets). https://www.taoglas.com/datasheets/UWC.20.pdf and https://www.taoglas.com/wp-content/uploads/pdf/UWC.20-Support-Application-Notes.pdf
- Do not place a battery or LCD near the antenna (general embedded-antenna guidance). https://www.mwrf.com/21128361
- Board orientation toward the phone: community advice is to face "the non-component side of the board toward the phone" (quoted in `ios_ni.md`). https://forum.qorvo.com/t/dwm3001cdk-iphone-16-demo-not-working/25626
- Floor geometry (derived, not sourced): antenna 1 cm above the floor, phone 1 m up, 5 m away: the reflected path is about 2 * 0.01 * 1 / 5 = 4 mm longer than the direct path (13 ps), far below the about 60 cm resolution of a 500 MHz UWB pulse, so the two merge; a near-grazing floor reflection is close to phase-inverted, so the first path is attenuated. The direct path also arrives about 11 degrees above the board plane, where a flat-mounted board's pattern is unknown.

Not confirmed: the DWM3001C antenna radiation pattern and its nulls (in the module datasheet figure, not loaded); measured ranging error for a board lying flat on a floor; any drop or shock rating for the kit.

## Recommended puck for tonight

1. Flash each board once from the Mac: micro-USB data cable into J9 (J-Link), SEGGER J-Flash Lite (free from segger.com, accept the terms, no account), device nRF52833, file `DWM3001CDK-QANI-FreeRTOS_full_QNI_3_0_0.hex`. Watch for charge-only cables.
2. Power each puck with its own USB battery bank: bank USB-A (or USB-C) into a micro-USB cable into the board. If a bank switches itself off after a few seconds, move the cable to J9 (the J-Link OB adds 10 to 15 mA of load), use a bank with an always-on or low-current mode, or use a wall adapter for the demo table.
3. Mount: board standing upright (antenna end up), 15 cm or more above the floor (a cup or box works), non-component side facing the expected phone positions, bank below the board and not behind the antenna, no metal within a few centimetres.
4. Optional diagnostic host, one puck only: UNO Q powered by a 5 V / 3 A PD supply into a USB-C hub/dongle with PD pass-through (not Apple); the board's J9 into a hub USB-A port with a data cable. On the UNO Q over SSH (not App Lab): install SEGGER J-Link for Linux arm64 and run `JLinkRTTLogger` (device NRF52833_XXAA, SWD) to capture QANI's RTT log; `bleak` over SSH for BLE scanning. The iOS app remains the source of truth for distances.
5. Skip the Android host tonight. Use the Android phone only as an emergency OTG power source (USB-C to micro-B cable) for one puck.

## What a real fire puck would need

- Direction on the puck itself: a dual-port DW3120/DW3220-class radio (PDoA, about 5 degree sigma) or a three-antenna array for 3-D AoA, instead of range differences between two single-antenna boards; if range differences are used, a rigid baseline of 50 cm or more and per-unit differential delay calibration.
- An antenna held off the floor whatever way the puck lands: a self-righting weighted body with a short mast (15 cm or more), radome of RF-transparent plastic, no metal within a few millimetres, battery away from the antenna.
- Heat, water and shock: high-temperature cells and enclosure, potting, a drop rating; the DW3000 is rated -40 to +85 C ambient.
- Firmware that streams ranges, link quality and NLOS indicators (first-path vs peak power) over a radio link to command, not RTT; puck-to-puck ranging to self-survey the anchor geometry after a throw.
- Per-unit antenna-delay calibration stored in OTP, plus wall and body NLOS bias models in the fusion filter, and outlier rejection for the metre-level phone outliers.
- Regulatory approval for the radios, and a plan for phones that are locked, in pockets or out of field of view (see `ios_ni.md`).
