# Sandtable — interface contracts

The interfaces between the parts of Sandtable: frames, data bundles, Python APIs, and the HTTP and WebSocket API between the server and the board. It was written before any code, as the contract for a team of parallel builders. The bench's cap on concurrent agents was already reached when they were to be spawned, so the lead built every part alone against this same contract; it is kept as the architecture reference. Where the code later went further (the guided exercise mode, the `/api/vision` and `/api/unit/assign` endpoints, `walls_crossed`, the `site` field of a unit, `url` on live aerial images), the additions are additive and are listed in section 7.

## 0. The product in three sentences

Sandtable is a live incident-command table for fire crews. An AI command agent builds a pre-incident plan for a real commercial building from three layers (CoStar building record, Vexcel aerial imagery, Matterport 3D twin), then UWB tags (crews, or tokens on a scaled exercise rig) are tracked inside the twin, and the agent runs accountability: no-motion MAYDAY, rescue-team routing, re-planning when a corridor or stair is lost, after-action report with observations written back to the twin and corrections filed against the record. Sponsor data comes through typed adapters with `live` and labelled `fixture` modes; the UWB side consumes the bench's shared uwb-kit stream (`../uwb-kit/INTERFACE.md`, read it).

## 2. Coordinate frames

- **site** frame: what the uwb-kit publishes. Metres on the physical rig, z up.
- **bldg** frame: the twin. Metres, x and y in the floor plane, z up, right-handed. Origin and axes are those of `twin.json`. Every position the app shows or reasons about is in this frame, plus a floor id.
- **geo**: WGS84. `twin.georef = {"origin": {"lat","lon"}, "bearing_deg": b}` where the origin is bldg (0,0) and `b` is the compass bearing (clockwise from north) of the +x axis. With `east = x*sin(b) - y*cos(b)` and `north = x*cos(b) + y*sin(b)`: `lat = lat0 + north/111320`, `lon = lon0 + east/(111320*cos(lat0))`.
- **aerial pixel** (ortho images): linear inside the image `bbox = [west, south, east, north]`: `px = (lon-west)/(east-west)*width`, `py = (north-lat)/(north-south)*height`.
- **Registration** site -> bldg is a 2-D similarity transform (uniform scale `s`, rotation, translation, optional mirror), fitted from two or more point pairs. `s` is "metres of building per metre of rig": about 9 to 30 on an exercise rig, 1.0 live. Default registration (no pairs given): centre of the anchors' bounding box onto the centre of the exercise floor outline, long axis onto long axis, `s = max(L_floor/L_rig, W_floor/W_rig)` so the whole floor lies inside the anchor rectangle (or `SANDTABLE_SCALE` when set).

## 3. Data bundles (JSON files under `fixtures/`, same shapes in live mode)

Placeholders written by the lead are in place now so that everybody has data to code against: `fixtures/building/twin.json` (generated by `scripts/build_twin.py`), `fixtures/building/site.json` and `fixtures/aerial/aerial.json` (hand-written, `"placeholder": true`). **Open them and read them; they are the schema by example.** B1 and B2 replace them with the real ones in the same shapes. Nobody may hard-code dimensions, room ids, suite numbers or coordinates from the placeholders: always read the bundle.

### 3.1 `twin.json` (`sandtable.twin/1`) — the Matterport layer, normalised

`source` (`kind`: `synthetic-fixture`|`matterport-live`, `synthetic`, `note`), `model` (`id`, `name`, `address`), `georef`, `exercise_floor` (floor id the rig maps to), and lists:

- `floors[]`: `id`, `index`, `label`, `elevation_m`, `outline` (polygon `[[x,y],...]`), `modelled` (bool: has rooms and a graph).
- `rooms[]`: `id`, `floor`, `kind` (`suite`|`corridor`|`stair`|`lobby`|`elevator`|`restroom`|`mechanical`), `label`, `suite` (string or null; joins to `site.tenants[].suite`), `polygon`, `area_m2`, `height_m`.
- `walls[]`: `floor`, `a`, `b` (segments; doors are not cut out of them).
- `doors[]`: `id`, `floor`, `at` `[x,y]`, `width_m`, `rooms` `[inner, outer]`, `kind` (`door`|`stair_door`|`opening`|`exit`), `node`.
- `stairs[]`: `id` (`stairA`...), `label`, `room`, `door`, `floors[]`, `discharge` (text, which side it exits to), `standpipe` (bool), `roof_access`.
- `sweeps[]` (Matterport pano locations): `id`, `node`, `floor`, `room`, `position` `[x,y,z]`, `neighbors[]`.
- `tags[]` (Matterport tags): `id`, `kind` (`standpipe`|`electrical`|`extinguisher`|`hazard`|`refuge`|`observation`|...), `label`, `floor`, `position` `[x,y,z]`, `description`.
- `graph`: `nodes[]` (`id`, `floor`, `at` `[x,y]`, `room`, `kind`: `sweep`|`door`|`stair`|`exit`) and `edges[]` (`a`, `b`, `len_m`, `via`: `"door:<id>"` or null). Undirected.

### 3.2 `site.json` (`sandtable.site/1`) — the CoStar layer plus public context

- `property`: `property_id`, `name`, `address`, `city`, `state`, `zip`, `lat`, `lon`, `property_type`, `building_class`, `rba_sf`, `typical_floor_sf`, `stories`, `year_built`, `year_renovated`, `construction`, `sprinklers`, `elevators`, `parking_spaces`, `parking_ratio`, `percent_leased`, `height_m`, `owner{name,phone}`, `property_manager{name,phone,after_hours_phone}`. A field with no truthful value in fixture mode is `null`.
- `field_sources`: per property field `{ "source": "...", "synthetic": bool }`.
- `tenants[]`: `tenant_id`, `name`, `suite`, `floor` (int), `sf`, `industry`, `naics`, `lease_expiration`, `life_hazard` (text or null), `hazmat` (text or null), `source`, `synthetic`.
- `available_spaces[]`: `suite`, `floor`, `sf`, `status`, `source`, `synthetic`.
- `footprint`: GeoJSON Polygon (lon, lat).
- `sides`: `{"A": {"bearing_deg", "street", "note"}, "B": ..., "C": ..., "D": ...}`. Side A is the address side; B, C, D follow clockwise seen from above (fire-service convention). `bearing_deg` is the outward normal of that side.
- `context`: `hydrants[]` (`id`, `lat`, `lon`, `source`, `synthetic`), `fire_stations[]` (`name`, `lat`, `lon`, `distance_m`, ...), `apparatus_positions[]` (`id`, `label`, `lat`, `lon`, `side`), `entrances[]` (`id`, `label`, `lat`, `lon`, `side`, `leads_to`: stair id), `permits[]`.

### 3.3 `aerial.json` (`sandtable.aerial/1`) — the Vexcel layer

`images[]`: `id`, `kind` (`ortho`|`oblique`), `path` (relative to the project root; the server serves `fixtures/` at `/fixtures/`), `bbox` `[west,south,east,north]` (ortho), `width`, `height`, `gsd_m`, `capture_date`, `heading_deg` (oblique look direction, else null), `source`, `synthetic`. There is always an image with `id: "ortho"`.

### 4.2 B2 — `sandtable.spatial`

```python
from sandtable.spatial import Twin, Registration, fit_similarity, default_registration, plan_anchor_drops, hose_stretch

twin = Twin(twin_dict)
twin.data                 # the dict
twin.exercise_floor       # "f3"
twin.locate(x, y, floor=None) -> {"floor", "room": id|None, "room_label", "room_kind", "suite", "node", "sweep", "snapped": [x, y], "off_map_m": float}
        # node = nearest graph node that is in the same room when possible; snapped = nearest walkable point; off_map_m = 0 inside the floor
twin.route(src, dst, blocked=(), floor=None) -> {
        "ok": bool, "reason": str | None, "nodes": [...], "polyline": [[x, y], ...], "length_m": float,
        "rooms": [room ids in order], "doors": [door ids in order],
        "src_resolved": {...}, "dst_resolved": {"kind", "id", "label"},
        "steps": [{"text": "Left out of Stair A into the West corridor", "at": [x, y], "dist_m": 6.0}, ...]}
        # src / dst accept: [x, y] | node id | room id | door id | stair id | suite number string ("304") | "exit" (dst only: best reachable stair)
        # blocked: refs to avoid: node id, door id, room id (all nodes in that room), stair id, or an edge "n012-n013"
        # a blocked ref that contains the src or dst itself does not make the route fail for that end
twin.nearest_exit(src, blocked=()) -> route dict (dst_resolved is the stair)
twin.exits() -> [{"id", "label", "room", "door", "node", "discharge", "standpipe"}]
twin.room(room_id) / twin.rooms(kind=None) / twin.door(id) / twin.node(id) / twin.tags(kind=None) / twin.stair(id)
twin.resolve(ref) -> {"kind", "id", "label", "at": [x, y], "node"}     # same refs as route()
twin.to_geo(x, y) -> [lat, lon];  twin.from_geo(lat, lon) -> [x, y]
twin.crosses_wall(p0, p1) -> bool      # the segment passes through a wall more than 0.6 m from any door
twin.describe() -> compact dict for LLM prompts: floor size, rooms by kind (label, suite, area), stairs, tags, corridor topology

class Registration:  scale: float; .apply(x, y) -> (X, Y)  # site -> bldg;  .invert(X, Y) -> (x, y);  .to_dict() / Registration.from_dict(d)
fit_similarity(site_pts, bldg_pts, allow_mirror=False) -> Registration        # least squares, >= 2 pairs
default_registration(anchors: dict[str, dict], twin: Twin, scale: float | None = None) -> Registration   # section 2
plan_anchor_drops(twin, floor=None, k=4) -> {"anchors": [{"id": "A1", "at": [x, y], "near": "Stair A door"}], "coverage_pct": float, "mean_visible": float, "method": str}
        # choose k drop points (stair doors, corridor junctions) that maximise the share of walkable nodes with line of sight to >= 3 anchors (walls block, doors do not)
hose_stretch(twin, site: dict, target, stair="stairA", apparatus_id="E1", standpipe=True) -> {
        "outside_m", "vertical_m", "inside_m", "total_m", "lengths_50ft": int, "via": str, "notes": [str]}
        # outside: apparatus -> entrance (geo distance from site.context); vertical: stairs to the floor (standpipe: hose starts at the outlet one floor below); inside: twin.route(stair, target)
```

### 4.3 B3 — `sandtable.incident`, `sandtable.server`, `sandtable.hubclient`, `sandtable.director`, `sandtable.demo`

```python
from sandtable.incident import Incident
inc = Incident(twin, provider, emit)          # emit(msg: dict) broadcasts a WebSocket message (section 5.2)

inc.snapshot() -> dict            # DISCRETE, deterministic state for agent prompts (no clock times, no raw coordinates):
#   {"phase": "standby|preplan|operations|mayday|rescue|egress|terminated",
#    "units": [{"id": "E1", "label": "Engine 1", "kind": "engine|rit|truck", "physical": true, "status": "staged|interior|mayday|exiting|out",
#               "floor": "f3", "room": "r304", "room_label": "Suite 304", "suite": "304", "node": "n045",
#               "assignment": {"task": "attack", "target": "r304", "target_label": "Suite 304"} | None}],
#    "hazards": [{"id": "hz1", "ref": "rcN", "kind": "blocked", "label": "North corridor", "note": "..."}],
#    "mayday": {"unit": "E1", "room": "r304", "room_label": "Suite 304", "reason": "no_motion|button|manual"} | None}
inc.state() -> dict               # full continuous state = the WebSocket "state" message (5.2)
inc.units                         # dict id -> unit dict
inc.blocked_refs() -> set[str]

# actions (the agent's action tools call these; each one adds a timeline entry and broadcasts)
inc.radio(sender: str, to: str, text: str, priority: str = "routine")          # routine | urgent | emergency
inc.assign(unit_id: str, task: str, target=None, via: list[str] | None = None) -> dict
        # task: attack | search | rit_rescue | exit | stage | hold. target: any ref twin.route accepts (or a unit id: go to that unit).
        # Computes the route from the unit's current node with current hazards blocked (plus `via` as required waypoints if given),
        # stores it on the unit, returns {"ok", "route": {...}} . Auto-followers start moving.
inc.mark_hazard(ref: str, kind: str = "blocked", note: str = "", source: str = "agent") -> dict   # kind: blocked | fire | collapse | smoke
inc.clear_hazard(hazard_id: str)
inc.request_resource(what: str, reason: str) -> dict
inc.declare_mayday(unit_id: str, reason: str, source: str = "reflex")
inc.resolve_mayday(unit_id: str)
inc.add_observation(text: str, unit_id: str | None = None, position: list[float] | None = None, kind: str = "observation") -> dict
        # writes a tag through provider.matterport.add_tag at the unit's position
inc.timeline                      # list of {"t", "t_rel", "kind", "text", "unit"}
```

Reflex layer (deterministic, runs on every position update; thresholds from `config.py`):

- Units: `E1` "Engine 1" (kind `engine`) bound to the first tag in `hello.nodes`; `RIT` "Rescue team" (kind `rit`) bound to the second tag when there is one, otherwise a **virtual** unit (`physical: false`) the server moves itself. Units are positioned by `Registration.apply` then `Twin.locate` with hysteresis on room changes (do not flip rooms on a single noisy sample).
- After the alarm, a physical unit that is `interior` and stays within `NO_MOTION_RADIUS_M` for `NO_MOTION_S` -> `declare_mayday(reason="no_motion")`. A kit `button` event from its tag -> mayday (`reason="button"`). Units with task `hold`/`stage` or standing in a stair are exempt.
- A mayday creates situation `mayday`; RIT reaching within `CONTACT_M` of the mayday unit creates `contact`; a new hazard that invalidates any active route (or any hazard while a mayday is open) creates `hazard`; both units in a stair after an `exit` assignment creates `all_out` and ends the incident (`terminated`), after which the server calls `agent.run_after_action()`.
- **Auto-followers**: a unit advances along its assigned route at `WALK_SPEED_MPS` when it is virtual, or when the hub is simulated and the unit is not being driven by the director or by a user drag. For simulated tags this is done with the hub's `POST /sim/teleport` (in site coordinates, through `Registration.invert`), so positions still pass through the kit's noisy ranging and solver. With real hardware physical tags are never moved by software. A follower whose route is invalidated by a hazard stops at the last node before the hazard until it is reassigned.
- Situations are queued and handed to the agent one at a time: `await agent.handle(situation)`. Situation = `{"seq": int, "kind": "mayday|hazard|contact|all_out|air_low", "unit": id | None, "data": {...discrete...}, "snapshot": inc.snapshot() at event time}`.
- If the agent has not issued any action `AGENT_FALLBACK_AFTER_S` after a `mayday`, `hazard` or `contact` situation, the reflex policy acts (assign RIT to the mayday unit by the shortest unblocked route; on contact assign both to `exit`) and the timeline says so.

`sandtable.hubclient`: consumes `UWBKIT_URL` exactly as `../uwb-kit/INTERFACE.md` specifies, using the kit's own client (`from uwbkit.client import AsyncStream, Kit`); exposes the last `hello`, `anchors`, `pos` per tag and `event`s; wraps `Kit.teleport` / `Kit.sim_control`. Do not write a ranging or solving stack and do not write a mock hub: **the kit is READY** (read `vendor/uwbkit/READY`), it is vendored at `vendor/uwbkit/` and installed in the project `.venv`. `sandtable.demo --hub sim` starts this project's own hub as a subprocess (`[sys.executable, "-m", "uwbkit", "hub", "--source", "sim", "--scenario", "hardware/scenarios/<file>.json", "--port", str(HUB_PORT)]`) and stops it on exit; `--hub url:...` attaches to an existing hub; `--hub serial:auto` / `udp:...` / `replay:...` are passed through to the kit as `--source`. Never POST to the shared hub on port 1800. Scenario files (`hardware/scenarios/`): anchors define the rig; tags only need a start position, because in sim the director and the followers move them with `/sim/teleport` (check that a teleported tag stays where it was put; if the kit's path playback moves it back, give the tags a single-waypoint path or use `/sim/control`).

`sandtable.director`: the SIM-only storyboard autopilot (condition-based, never wall-clock based, so the discrete state at each agent call is identical on every run):

1. `alarm` -> wait until the pre-plan is done.
2. Drive E1 (teleports at follower speed) from the Stair A door along the corridor into the scenario's fire room (a suite whose tenant has a `life_hazard`, chosen from the bundle, not hard-coded). Assign E1 `attack`.
3. E1 holds still -> reflex mayday -> wait until the agent has assigned RIT and RIT has covered 40% of its route.
4. Inject a `blocked` hazard on the corridor segment RIT is about to use (choose the edge/room so that an alternative route exists) -> wait for the agent's re-plan -> wait for `contact`.
5. Wait for the agent's egress plan -> E1 moves out together with RIT -> `all_out` -> wait for the after-action report. Done.

### 4.4 B4 — `sandtable.agent`

```python
from sandtable.agent import CommandAgent
agent = CommandAgent(provider, twin, incident, emit)     # emit(msg: dict): same broadcaster as the server's
await agent.run_preplan() -> dict          # the pre-plan object; also emits {"type": "preplan", ...}
await agent.handle(situation: dict) -> dict  # deliberates with tools and calls incident actions; returns {"actions": [...], "backend": ...}
await agent.run_after_action() -> dict     # the AAR object; also emits {"type": "aar", ...}
agent.busy -> bool
agent.backend -> "replay" | "claude-cli" | "anthropic"
```

- One LLM wrapper `sandtable/agent/llm.py` with the three backends of the bench `CLAUDE.md` (`anthropic` SDK; `claude-cli` = `claude -p ... --output-format json < /dev/null`; `replay` = `fixtures/llm_cache/<sha256 of the canonical request>.json`). `LLM_RECORD=1` writes real responses into the cache. Never hand-write a model output.
- Tool calling is prompted JSON, the same on every backend: the model answers with one JSON object, either `{"thought": "...", "tool": "<name>", "args": {...}}` or `{"thought": "...", "final": {...}}`. Loop until `final` or `AGENT_MAX_STEPS`.
- **Determinism for replay:** prompts are built only from discrete facts (`situation["snapshot"]`, room/node ids, tool results computed from the snapshot's nodes, lengths rounded to whole metres). No timestamps, no raw coordinates, no floats with noise. Then the storyboard hits the cache on every run.
- On a replay miss with no live backend, or on an LLM error, the agent runs a deterministic fallback policy and labels every event `backend: "reflex-fallback"`.
- Every step emits an event (5.2 `agent`). In replay mode sleep `REPLAY_PACE_S` between steps.

Tools offered to the model (names are part of the UI's vocabulary):

| `POST /api/reset` | back to standby, clears units' assignments, hazards, timeline, agent state |

### 5.2 WebSocket `GET /ws` (server -> client JSON, one object per frame)

- `hello`: `{"type": "hello", "simulated": bool, "hub": {"connected": bool, "source": "...", "profile": "..."}, "modes": {"costar", "matterport", "vexcel", "llm"}, "labels": {...}, "registration": {"scale": 9.0, ...}, "exercise": bool, "no_motion_s": 8.0}` (sent on connect and whenever any of it changes)
- `state` (at `STATE_HZ`): `{"type": "state", "t": unix, "phase": "...", "elapsed_s": 0.0, "units": [Unit], "hazards": [{"id", "ref", "kind", "label", "note", "geometry": {"kind": "room|edge|point", "polygon"|"polyline"|"at"}}], "mayday": {...} | null, "anchors": [{"id", "x", "y"}] (bldg frame), "agent_busy": bool, "storyboard": {"running": bool, "step": "..."}}`
  - `Unit`: `{"id", "label", "kind", "physical": bool, "tag": "T1" | null, "status", "x", "y", "floor", "room", "room_label", "suite", "node", "sweep", "heading", "speed", "q", "sigma_m" (1-sigma position uncertainty in building metres = sqrt(max cov) * scale, null for virtual), "still_s", "air_pct", "time_in_s", "assignment": {"task", "target", "target_label"} | null, "route": {"polyline": [[x, y], ...], "length_m", "valid": bool} | null, "geo": {"lat", "lon"}}`
- `agent`: `{"type": "agent", "run": "preplan" | "mayday#2" | ..., "phase": "preplan|command|aar", "step": int, "kind": "start|thought|tool_call|tool_result|action|final|error", "backend": "replay|claude-cli|anthropic|reflex-fallback", "text": "one readable line", "tool": "route", "args": {...}, "result": {...small...}, "t": unix}`
- `radio`: `{"type": "radio", "t", "from": "COMMAND", "to": "RIT", "text": "...", "priority": "routine|urgent|emergency"}` (the UI may speak it)
- `timeline`: `{"type": "timeline", "entry": {"t", "t_rel", "kind", "text", "unit"}}`
- `alert`: `{"type": "alert", "level": "mayday|warn|info", "text": "...", "unit": "E1" | null}`
- `preplan`, `aar`: the objects of 4.4
- `reset`: `{"type": "reset"}`

On connect the server sends `hello`, then the latest `preplan`/`aar` if any, then the backlog of `agent`, `radio` and `timeline` messages of the current incident, then live traffic.

## 7. Additions made while building (all additive)

- `POST /api/storyboard` takes `"mode": "auto" | "assist"`. `auto` (SIM only) moves every crew; `assist` lets a person move Engine 1 (real boards, or a drag in the UI) and is allowed on real hardware. `state.storyboard` carries `mode`, and a `step` that starts with `YOUR MOVE` is a cue for the person.
- `GET /api/vision/{image_id}.png`: the annotated aerial image the agent's vision tool sent to the model. The `preplan` object has `vision: [{image, question, answer, source}]`.
- `POST /api/unit/assign` `{unit, task, target}`: a manual order from the board.
- `state.units[].site`: the tag's raw position in the rig frame (used by `python -m sandtable.calibrate`). `state.hub_connected`.
- WebSocket message `tag` `{type: "tag", tag: {...}}` when an observation is pinned in the twin.
- `Twin.walls_crossed(p0, p1)`; `plan_anchor_drops()` returns `coverage_pct` (3 or more anchors within one wall) and `line_of_sight_pct`.
- Live aerial images carry `url` (served under `/live/vexcel/`); fixture images are served from their `path` under `/fixtures/`.
- `site.json` has `frame` (the fitted footprint rectangle), `cross_checks` (disagreements between layers found when the bundle was built) and `open_data` (sources).
- Tool `outside_context` (one call for sides, apparatus, entrances, hydrants, stations, height) was added to the agent's catalogue.
